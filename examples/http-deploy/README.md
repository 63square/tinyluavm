# `http-deploy` example

A complete, runnable example of fetching the entire data plane —
macro-VM AST and user program — from an HTTP server at runtime,
decoding the JSON response, and running the user program through
the micro-VM.

Useful when:

* The user program is generated/updated server-side (e.g. by an
  authoring tool, a CI pipeline, a marketplace) and you don't want
  to redeploy your Roblox script every time it changes.
* You want to A/B-test variants of a script without re-publishing.
* You want one shared `macrovm-ast.json` payload reused across many
  user programs hosted at different URLs.

In a real Roblox deployment this is exactly what `HttpService:GetAsync`
is for.


## Layout

```
examples/http-deploy/
├── README.md              you are here
├── build_and_run.py       driver: compile + predecode + serve + run luau
├── server.py              tiny HTTP server (importable + runnable)
├── launcher.luau          ★ the launcher: fetches, decodes, calls micro()
├── user.luau              a sample user program (computes some primes)
└── staged/                ↑ assembled by build_and_run.py, gitignored
    ├── tinyvm.luau            copy of src/tinyvm.luau
    ├── jsondec.luau           copy of ../json-deploy/jsondec.luau
    ├── launcher.luau          copy of ../launcher.luau
    ├── httpget.luau           HTTP-GET shim (mock for standalone luau)
    ├── config.luau            launcher reads {payloadUrl, serverInfo}
    └── payload.json           the actual JSON served over HTTP
```

## What's actually HTTP and what's mocked

The HTTP server is **real**:

```bash
# In one terminal:
python examples/http-deploy/server.py examples/http-deploy/staged/payload.json --port 8765

# In another:
curl http://127.0.0.1:8765/payload.json | jq '.m[1][1:5]'
```

You can `curl` the payload, `jq`-explore it, anything you'd do with
a real HTTP endpoint.

The driver also does a real HTTP `GET` (Python `urllib.request`)
to validate the server's response before staging the Luau files.

**What's mocked**: the actual fetch *from inside `luau`*. Standalone
`luau` is a fully sandboxed VM with no I/O, no network. So
`staged/httpget.luau` is generated by the driver to return the
pre-fetched body when the launcher asks for the configured URL:

```lua
return function(url)
    if url == _expectedUrl then return _body end
    error("httpget shim: unexpected URL " .. tostring(url), 0)
end
```

On Roblox you'd replace it with a one-liner:

```lua
local HttpService = game:GetService("HttpService")
return function(url) return HttpService:GetAsync(url) end
```

— and nothing else about the launcher changes. The architecture is
identical.


## How it works

### Build pipeline (offline, in Python)

1. Compile `src/macrovm.luau` (one-time, cached in `build/macrovm.bin`).
2. Compile `user.luau` to a temporary `.bin`.
3. `tools/predecode.py build/macrovm.bin staged/payload.json
   --for-micro --json --user user.bin` predecodes both into one JSON
   document: `{"m": [<macroK>, <macroF>], "u": [<userK>, <userF>]}`.

### Runtime pipeline

1. The driver starts the HTTP server (`server.py`) in a daemon thread,
   serving the payload at `/payload.json` on an OS-picked port.
2. The driver does a real `GET` to verify the server, captures the
   body and the `Server:` response header, then stages the Luau files.
3. The launcher runs under `luau`:

   ```lua
   local micro    = require("./tinyvm")
   local decode   = require("./jsondec")
   local httpGet  = require("./httpget")
   local config   = require("./config")

   local body      = httpGet(config.payloadUrl)
   local inputData = decode(body)

   local userEnv = setmetatable({}, {__index = _G})
   userEnv._G    = userEnv
   userEnv.hostInfo = { -- ... server metadata for the user program ... }

   micro(inputData, userEnv, "user.luau")
   ```

4. The user program runs. It can see the URL it was fetched from,
   the server's `Server:` header, the payload byte count -- because
   the launcher passed all those facts through `hostInfo`.


## Where this fits in the deployment matrix

|                                  | split deploy            | json deploy             | http deploy (this)            |
|----------------------------------|-------------------------|-------------------------|-------------------------------|
| Macro-VM data lives in           | ModuleScript            | ModuleScript            | HTTP endpoint                 |
| User program lives in            | ModuleScript            | ModuleScript            | HTTP endpoint (same payload)  |
| Update flow                      | re-publish Roblox       | re-publish Roblox       | push to server, no redeploy   |
| Network dependency               | none                    | none                    | yes (HttpService)             |
| Best for                         | static deployment       | static deployment       | dynamic / hot-swap deployment |

If the user program rarely changes, split or json deploy is fine —
both are completely offline. http deploy adds a network round-trip
on every cold start, but lets you ship updates without re-publishing
the Roblox place.


## Customizing

* **Authentication**: Roblox `HttpService:GetAsync` takes a second
  argument for arbitrary headers. Pass an auth token, signed URL, etc.
* **Caching**: the launcher can stash `inputData` (or even the raw
  body) in a `ModuleScript`-level table to avoid re-fetching across
  reloads. Invalidate on a version check.
* **Multiple user programs**: keep one shared `macrovm-ast.json` URL
  (cacheable) and per-user `user-ast.json` URLs. Combine them into
  `inputData = {m = ..., u = ...}` in the launcher.
* **Failure handling**: wrap `httpGet` in `pcall`; fall back to a
  baked-in `ModuleScript` payload if the server is unreachable.

See the sibling [`json-deploy/`](../json-deploy/) for the offline
version of the same JSON payload shape.
